build on MacOS
==============

Ceph does not have macOS CI, so macOS is a best-effort platform. What follows
was verified on macOS 26.6 (Darwin 25.6) on Apple silicon, with the Apple clang
that ships with the Command Line Tools. No third-party toolchain is needed; a
separate ``brew install llvm`` is not required.

The client libraries, the mon, the OSD, the mgr, the MDS, the RGW and the
offline tools all build and run, and a ``vstart.sh`` cluster backed by
``memstore`` runs all five daemons together. BlueStore does not build, so the
OSD is memory-backed only.

``do_cmake_macos.sh`` enables the mon, the OSD, the client libraries and the
tools. The mgr, the MDS and the RGW are left off there, not because they fail
to build but because each needs packages beyond the base set; `Optional
daemons`_ covers what to install and which options to pass.

Dependencies
------------

::

  brew install cmake ninja boost ccache openssl@3 snappy lz4 zstd nss \
      icu4c sqlite libevent utf8proc c-ares

``src/pybind`` requires Cython unconditionally, even when the Python bindings
are not wanted, and the options tables are generated by a script that needs
PyYAML. Homebrew's Python is externally managed, so install into a virtualenv
rather than into the Homebrew prefix::

  uv venv --python 3.12 .venv
  uv pip install --python .venv/bin/python cython pyyaml setuptools \
      prettytable python-dateutil

``setuptools`` is needed because the ``setup.py`` files still import
``distutils``, which is no longer in the standard library; ``prettytable`` is
imported by the ``ceph`` command line tool, and ``python-dateutil`` by the
``rbd_support`` mgr module.

Only a few of the submodules are needed::

  git submodule update --init src/fmt src/BLAKE3 src/xxHash src/rocksdb \
      src/zstd src/googletest src/utf8proc \
      src/erasure-code/jerasure/jerasure src/erasure-code/jerasure/gf-complete

Do not pass ``--depth 1`` here. Several of these repositories have the pinned
commit off the tip of the default branch, and a shallow clone silently leaves
the submodule on ``master`` instead; ``git submodule status`` shows a leading
``+`` when that has happened.

Configuring and building
------------------------

``do_cmake_macos.sh`` in the top of the source tree wraps the required
options - it points CMake at the keg-only Homebrew packages, selects the
virtualenv interpreter, and turns off what cannot build here::

  ./do_cmake_macos.sh
  ninja -C build vstart-base librbd rbd

Build named targets. The ``all`` target is not expected to succeed, because it
also covers the components that have not been ported.

What builds
-----------

Client libraries::

  ceph-common librados librbd cephfs

Daemons::

  ceph-mon ceph-osd ceph-mgr ceph-mds radosgw rbd-mirror

Command line and offline tools::

  rados rbd crushtool osdmaptool monmaptool ceph-authtool ceph-conf
  ceph-dencoder ceph-erasure-code-tool ceph-kvstore-tool ceph-monstore-tool
  ceph-objectstore-tool ceph-diff-sorted librados-config neorados ceph-syn
  rbd-replay ceph-immutable-object-cache radosgw-admin

``ceph-dencoder`` loads its type modules from the install path, so point it at
the build tree::

  CEPH_LIB=$PWD/build/lib ./build/bin/ceph-dencoder list_types

Optional daemons
----------------

The mgr, the MDS and the RGW need extra packages and options rather than source
changes. Build them into a separate directory so the base configuration is left
alone.

The MDS needs only ``WITH_CEPHFS=ON``.

The mgr needs Boost.Python, and the ``boost`` formula ships the headers but
not the library. Homebrew has it in a separate formula, ``boost-python3``,
built against whichever ``python@3.x`` that formula happens to pin - which the
interpreter Ceph embeds then has to match. Rather than pin the whole build to
someone else's choice, let Ceph build Boost itself with
``WITH_SYSTEM_BOOST=OFF``; it builds Boost.Python against the same interpreter
as everything else, and needs no extra package. The cost is one Boost build
from source.

The RGW needs liboath and two more submodules::

  brew install oath-toolkit
  git submodule update --init src/libkmip
  git submodule update --init --recursive src/s3select

Then configure and build all three::

  BUILD_DIR=build-all ./do_cmake_macos.sh \
      -DWITH_SYSTEM_BOOST=OFF \
      -DWITH_MGR=ON -DWITH_CEPHFS=ON -DWITH_RADOSGW=ON \
      -DWITH_MGR_ROOK_CLIENT=OFF -DWITH_MGR_DASHBOARD_FRONTEND=OFF \
      -DWITH_RADOSGW_AMQP_ENDPOINT=OFF -DWITH_RADOSGW_KAFKA_ENDPOINT=OFF \
      -DWITH_RADOSGW_LUA_PACKAGES=OFF -DWITH_RADOSGW_D4N=OFF \
      -DWITH_RADOSGW_POSIX=OFF -DWITH_RADOSGW_DBSTORE=OFF \
      -DWITH_RADOSGW_SELECT_PARQUET=OFF
  ninja -C build-all vstart-base ceph-mgr ceph-mds radosgw radosgw-admin \
      cython_cephfs

``WITH_MGR_ROOK_CLIENT`` needs the ``rook-client-python`` submodule and the
dashboard frontend needs ``npm``; each RGW endpoint switched off above pulls in
another library. None are needed to run the daemons.

``cython_cephfs`` is not optional when the MDS is wanted. ``vstart.sh`` creates
the file system with ``ceph fs volume``, which the ``volumes`` mgr module
implements, and that module imports the cephfs Python bindings. Without them
the command does not exist, and vstart retries it forever rather than failing.

Running a test cluster
----------------------

BlueStore is not available, so run vstart against ``memstore``. Two environment
variables matter when the optional daemons are in play:

* ``radosgw`` daemonises by forking without exec, and something on its startup
  path reaches CFPreferences and so the Objective-C runtime, which is fatal
  after ``fork()`` on Darwin. It aborts before it can open its log file, with a
  backtrace consisting entirely of ``libobjc`` and ``CoreFoundation`` frames
  and no mention of Ceph. ``OBJC_DISABLE_INITIALIZE_FORK_SAFETY=YES`` avoids
  it.
* mgr modules are Python and load at runtime, so their dependencies have to be
  importable by the *embedded* interpreter, which does not see the virtualenv
  unless its ``site-packages`` is on ``PYTHONPATH``.

::

  cd build-all
  export OBJC_DISABLE_INITIALIZE_FORK_SAFETY=YES
  export PYTHONPATH=$PWD/../.venv/lib/python3.12/site-packages
  MON=1 OSD=1 MDS=1 MGR=1 RGW=1 ../src/vstart.sh -n --memstore -X

That brings up all five daemons::

  services:
    mon: 1 daemons, quorum a
    mgr: x(active)
    mds: 1/1 daemons up
    osd: 1 osds: 1 up, 1 in
    rgw: 1 daemon active (1 hosts, 1 zones)

RADOS and RBD both work, including image snapshots and clones::

  export CEPH_CONF=$PWD/ceph.conf
  ./bin/ceph -s
  ./bin/ceph osd pool create rbdpool 8 8
  ./bin/rbd create --size 128 rbdpool/img1

The S3 endpoint answers on port 8000; bucket create, object put, get, list and
delete all work against it.

A smaller cluster is often enough. ``MON=1 OSD=1 MDS=0 MGR=0 RGW=0`` against
the plain ``build`` directory needs none of the optional daemons and none of
the environment above.

Things worth knowing before they are hit:

* ``memstore`` keeps everything in memory, so data does not survive restarting
  an OSD, and a single-OSD cluster reports ``POOL_NO_REDUNDANCY``.
* ``memstore_device_bytes`` defaults to 1 GiB, and memstore serves close to a
  gigabyte a second, so a few seconds of an unbounded write test fills it. The
  OSD then correctly marks itself full and every subsequent write blocks, which
  looks like a hang. Bound the test - ``rados bench 5 write --max-objects 16``
  - or raise ``memstore_device_bytes``.
* Running without a mgr leaves the commands that mgr modules implement
  unavailable, and they hang rather than fail. That includes ``ceph pg stat``;
  ``ceph -s`` still works but reports an empty ``data`` section, because the PG
  and usage totals come from the mgr. ``ceph health detail`` and the daemons'
  admin sockets answer directly::

    ./bin/ceph --admin-daemon asok/osd.0.asok status
    ./bin/ceph --admin-daemon asok/osd.0.asok perf dump osd

* The mgr modules that fail to load do so for want of pip packages -
  ``requests``, ``cherrypy``, ``scipy``, ``urllib3``, ``cryptography`` - except
  ``devicehealth``, which needs ``WITH_LIBCEPHSQLITE``.

What does not build
-------------------

* BlueStore, and therefore any persistent OSD; it needs libaio or io_uring and
  the Linux block layer
* ``ceph-fuse``, which is untried; it would need macFUSE and ``WITH_FUSE=ON``.
  ``cmake/modules/FindFUSE.cmake`` already has an ``APPLE`` branch.

Notes
-----

* Darwin has no ``/proc``. ``PROCPREFIX`` is defined empty so the readers in
  ``common/util.cc`` and ``common/MemoryModel.h`` still compile; they return a
  runtime error instead.
* Darwin does not implement POSIX per-process timers, so the ``raise`` admin
  socket command is unavailable. Note that ``_POSIX_TIMERS`` is a poor proxy for
  this - Darwin defines it as ``-1``, meaning "declared, unsupported" - so the
  build probes for ``timer_create`` instead.
* Darwin has no ``posix_fadvise()``. The call is advisory, so it is stubbed
  out, and the ``POSIX_FADV_*`` values keep their Linux numbering because they
  reach their callers through configuration options.
* ``dump_tcp_info()`` returns false. Darwin exposes connection statistics as
  ``struct tcp_connection_info`` via ``TCP_CONNECTION_INFO``, which shares no
  fields with the Linux ``struct tcp_info``.
* CPU affinity and NUMA queries return ``-ENOTSUP``.
* ``vstart.sh`` uses ``ss`` to look for a free port, which Darwin does not
  have; the check silently does nothing and the randomly chosen port is used
  as-is.
* ``size_t`` is ``unsigned long`` on Darwin while ``uint64_t`` is ``unsigned
  long long``, so the two are distinct types where LP64 Linux makes them one.
  ``encode()`` and ``decode()`` are defined for the fixed-width types only, so
  anything encoding a ``size_t`` or a ``time_t`` builds on Linux and nowhere
  else. Naming the fixed-width type is the fix, and it leaves the encoding
  unchanged.
