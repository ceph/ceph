====================================================
Guidelines for BlueStore contributors using AI tools
====================================================

This document explains what we expect from pull requests to BlueStore that
were made with the help of AI tools. If a PR does not follow it, the team may
not review it. The goal is to respect the time of both contributors and
reviewers.

We do not discourage the use of AI tools. They have made it possible for users
to fix the bugs they hit themselves, instead of filing a tracker and waiting
for someone else to solve it.

We only ask that you use them with empathy for the reviewers and for the
project.

These guidelines are written mainly for bug fixes, but most of them apply to
features too.

Step 1: Search the tracker
==========================

Before anything else, search the tracker to see whether the problem you hit
has already been fixed, or at least reported. If you find a ticket, start the
conversation there: someone may already be working on a fix.

This saves you time and helps you use your AI tool where it is actually
needed.

Step 2: Create a tracker
========================

Bug fixes must reference a tracker ticket. The only exception is a bug
introduced by a recent change that has not been released yet.

If no tracker exists, please create one.

Please write the title and the problem description in your own words. You may
use AI tools to polish your text, but please do not have them write the ticket
for you. AI tools tend to over-explain the technical details of a bug without
giving its context: they are good at describing the trees, but miss the
forest. AI analysis of the bug is still welcome.

Title
-----

Please search the tracker to find out whether the problem is already known or
fixed. The title should describe what can be observed, for example:

* "LruOnodeCache causes assert on shutdown"
* "powerdown corrupts recently written object data"
* "ceph-bluestore-tool trim does not discard anything unless
  ``bdev_enable_discard=true``"

Please Note, the tracker title can always be changed when conditions for the
bug get better researched during the course of work.

Problem description
-------------------

The description should contain the context of the bug. The primary question it
should answer the following questions:

* How was the bug first noticed or suspected?
* Did you hit it during normal use? If so, what were you doing?
* If relevant, attach the observed assert or crash backtrace.

Note, this is about the original trigger for the bug, not the artificially
created environment that allowed  the replication of the bug.

Step 3: Describe the solution in the tracker
============================================

The tracker comments, can be used to describe the solution that was
chosen/not chosen to solve the bug. The intended readers are human. Make
formatting and flow of thought easy to consume.

Research
--------

Please share the research you did on the bug, including (but not limited to):

* experiments you ran and their results (passed / failed)
* the different options you tested

Solution
--------

Describe, in general terms, what the problem turned out to be. Often it is a
logical typo, a missed instruction, a forgotten condition, and so on. It is
not necessary to describe precisely what failed. This section has two goals:

* Set context for the reviewer, this should allow them to connect the dots
  when they read the code
* Provide a non-specialist understanding on how this bug can impact other
  parts of the project

Details
-------

Additional details may not be necessary. Reviewers will ask their questions on
the PRs for clarification and expect that the contributor explain their
choices and provide rationale.

If the PR was entirely generated by AI tools, it is recommended to attach the
session communication that was used to develop it.  AI analysis of the
execution chain, state changes and path leading to exposition of the bug is an
asset worth attaching to the ticket.

The detail section here can be skipped here if the description of the PR
contains the details.

Step 4: Pull request
====================

Again, the readers of the PR are human reviewers. Make the formatting and the
flow of thought easy to follow.

Title
-----

The title should describe the change made, not the bug it fixes. This makes it
easy to connect the title with the code change, which helps anyone looking
back through the history later.

Use one of these words in the title, or an equivalent:

* "fix": the PR changes something that was clearly meant to work differently
* "add" or "enhance": the problem was missing logic or a missing function

As usual for Ceph, the title starts with the component, for example
``os/bluestore: fix ...``.

Description
-----------

Explain what the problem was and how the change fixes it. In obvious cases you
do not need to write much. Favor readability over detail.

The description has three purposes:

* give the reviewer enough context to match it with the code
* let a non-specialist understand the change
* point out side effects of the change that are not immediately obvious

If the linked tracker already contains the problem and solution analysis, the
PR can simply refer to it. Otherwise, explain why the code change fixes the
problem. If the bug only shows up on a specific execution path, describe that
path.

Commits
-------

Do not hesitate to split the work into several commits. Aim for a short
solution, but not at the cost of a simple one.

If a logically simple fix needs a structural preparation step, use two
commits:

* the first commit refactors or moves code, with no change in logic
* the second commit makes the change that matters

If you find other minor defects related to the bug, fix them in separate
commits.

If you add a unit test, make it the first commit. This makes it easy to check
that the test fails before the fix is applied.

Unit tests
----------

Tests have to actually test something. Do not write tests that only happen to
pass along with the fix. Please check that your test fails when run without
the fix.

* A test that has to significantly tweak the environment is most likely a bad
  one.
* If reproducing the bug required a specific condition, the test should cover
  that condition and also logically similar ones.
* If the fix addresses a bug caused by random data, undefined behavior or
  uninitialized state, it is acceptable to skip the test.

If a unit test would need invasive changes to the code base, you may provide
manual reproduction steps instead, preferably as a script that reproduces the
problem.

Bad practices
=============

Impersonation
-------------

As the Ceph guidelines say, disclosing AI-assisted work is mandatory. See:
https://github.com/ceph/ceph/blob/main/doc/dev/developer_guide/ai-coding-assistants.rst

State which parts of your contribution were made with AI tools.

Do not post AI-generated review comments, or AI-generated answers to a
reviewer's questions, as if they were your own. Quoting an AI tool without
saying so is just as bad.

Comprehension
-------------

Writing a fix and checking a fix need very different levels of understanding.
To write a fix yourself, you need to understand the bug, the code, and how the
two interact. To read a fix that an AI tool wrote and confirm it looks right,
you need much less. Both can end in the same PR, but not with the same
understanding behind it.

This is not a problem in itself. Everyone relies on tools whose results they
could not produce on their own. The philosopher Daniel Dennett called this
"competence without comprehension". We do not require contributors to fully
understand every line their AI tool produced. There is no practical way to
check it, and it would not be useful.

It does mean reviewers cannot treat an AI-assisted PR like a hand-written one.
When a reviewer asks "why did you do it this way?", the author may not know.
If they ask the AI tool, it will give a convincing answer whether or not that
was the real reason. That is why this document asks for what was asked of the
AI tool, the AI's analysis of the bug, and tests that are shown to fail before
the fix. They give the reviewer the context a hand-written PR would carry in
its author's head.

So please be honest about how much you understand. "I checked the test fails
without the fix and passes with it, but I couldn't follow why X is needed" is
useful to a reviewer. A confident explanation copied from the AI tool is not.
