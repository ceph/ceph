* Owning and borrowed invocation share body-result and exception normalization.
  Borrowed handles are validated at their caller boundary; owning attempts use
  transactions already created by their source. Staged preparation remains inside
  the shared exception boundary; replay history, failed-attempt cleanup, commit,
  and publication stay with the owner. Ordinary values no longer need dummy expected/monostate storage.
  Implicit mutating leaf operations use the public owning Transactor instead of
  a separate transaction/retry wrapper.
  Functional transforms use ordinary range traversal without maintaining a row
  count that their callers do not consume; mutable callables remain borrowed.
  Exception-based leaf helpers accept ordinary value/void bodies; typed
  application rejection uses the owning/borrowed Transactor interfaces.

* Core relationship predicates borrow canonical interval-set storage instead of
  compiling it again. Scalar enclosure borrows its difference operands, and
  counting/emptiness observe emitted bounds without materializing their keys.
  Difference-bound adjustments borrow endpoints; only a cursor retained across
  callbacks materializes its new position.
  Arbitrary expressions still normalize when canonical traversal requires it.

* General set mutations reuse core interval assignment for strong publication.
  FDB (FoundationDB) construction/mutation share bounded geometry, and scalar/composite scans
  share selector compilation. Scalar emptiness/count checks borrow endpoint bytes;
  executable rvalues transfer them. Key concepts and ADL (argument-dependent lookup) adaptation live
  once in standard-only key.h; query.h no longer requires a prior base.h include or Ceph
  container dispatch.

* The complete set-operator family (&, |, -, ^, ~) delegates to named algebra
  operations. Explicit query::interval_set supports expression assignment and
  &=, |=, -=, ^= through assign_intersection, assign_set_union, assign_difference,
  and assign_symmetric_difference. assign_complement supplies unary mutation.
  General sets build a canonical replacement and swap on success; the single-
  interval intersection retains its storage-reuse fast path. Options survive
  empty results. Core/FDB overloads preserve their respective universes; bounded
  XOR (exclusive or) toggling is distinct from relative complement. See EXAMPLES.md.

* query::assign_intersection(range, bound) and range &= bound modify a concrete
  interval and return it by reference. The operator delegates to the named mutator;
  concrete value-producing intersection uses the same implementation. Borrowed
  core bound selection retains unchanged strings and lets temporary bounds donate
  tighter endpoints. Option conflicts, self-aliasing, open/closed boundaries, and
  ordinary-keyspace clamping keep their existing semantics. Lazy expressions remain
  value-producing. See EXAMPLES.md for usage and exception guarantees.

* Paged collection reserves from source cardinality rather than the requested
  maximum. Exact sizes use standard range sizing; bounded approximate sources use
  the C++26 reserve_hint CPO (customization point object) only when its library feature macro is available.
  Unlimited unsized streams grow from actual rows, and empty generic pages reserve
  no vector storage. Native single-window pages use the same collector over a
  capped decoded view, preserving returned-row reservation and avoiding decoding
  the continuation row.
  Suitable generic collections and page-result accessors support constant evaluation.

* Include fdb.h for the complete public interface. Lower-level ownership lives
  in base.h; transactions, transactors, and staged output live in transaction.h;
  direct key operations live in interface.h; and range traversal lives in
  scan.h.

* Use staged(output) to lazily copy the target for each transaction attempt, or
  staged(std::in_place, output) to start with a fresh value. Both publish only
  after a confirmed commit. See EXAMPLES.md for the Staged Proxies contract.

* transaction_result.h defines the shared completion/error vocabulary. Ordinary
  commit(txn), commit(txn, stamp), and owning Transactor invocations return this
  result family, preserving phase and commit history. Manual commit submits once;
  only an owning Transactor call replays the body. Completion has no with_result
  selector. A returned application error rejects the attempt; other ordinary
  values authorize commit. See EXAMPLES.md for result handling and uncertainty.

* txr(txn, body, args...) borrows an existing transaction for one synchronous
  invocation. It returns expected<T, transaction_failure<E>> with working data,
  without commit, recovery, stamp completion, or argument copying. Its failures
  use the same classification as owning results. Returning that expected to the
  owner preserves native recovery eligibility and application rejection, while
  the owner retains attempt counts and earlier uncertainty. Borrowed calls do not
  accept staged arguments; put staged output on the owning call.

* Standard expected and_then/transform compose typed results; keep the complete
  chain inside a Transactor invocation to capture throwing callbacks. and_then
  requires matching error types. The standalone example includes owned/borrowed
  execution, caller commit, application rejection, and centralized reporting.

* Managed execution defaults to retry_policy::no_replay_unknown: native recovery
  handles eligible failures until an attempt leaves its commit outcome uncertain.
  retry_policy::replay_unknown explicitly permits native recovery after uncertainty
  when the application can tolerate or deduplicate repeated database effects.
  Both policies retain native retry/timeout budgets and stop after commit
  observation failure. "Unknown" includes unknown_result, unconfirmed, and earlier
  uncertainty retained by the owner. The native error predicates keep their names.

* Native commit attempts produce that same completion result internally.
  Synchronous and asynchronous owners share failure classification, exception
  origin, stamp cleanup, and replay decisions. Read helpers omit completion.
  Single-shot leaf writes share native completion but preserve their caller's
  transaction when the leaf body fails before commit.

Network and Database Options:

Option containers now retain insertion order and repeated applications. The
option_map alias and associative operations are removed; use emplace_back(),
append_range(), replace_all(), and erase(). Mutable lists support writable
iteration over codes and values; const lists and cbegin()/cend() retain const
iterators. Reordering entries changes their application order.
Database helpers accept transaction options immediately after their handle. Lazy reads
retain an owning snapshot, and replay restores nonpersistent entries in their original order. See the
Options chapter in EXAMPLES.md for migration and lifetime details.

Pass a network_options object to create_database(netopts) to configure only the
client network. This keeps default source resolution and empty database options;
create_database(dbopts, netopts) configures both. Network options take effect only
on the first client-network initialization.

There are various database at network settings that can be adjusted; see the "options" test for some examples of using
the network_options and database_options structures. But what may be tweaked, you ask? Excellent question-- and when

Equivalence with FDBStreamingMode:

FDB_STREAMING_MODE_ITERATOR

The caller is implementing an iterator (most likely in a binding to a higher level language). The amount of data returned depends on the value of the iteration parameter to fdb_transaction_get_range().

FDB_STREAMING_MODE_SMALL

Data is returned in small batches (not much more expensive than reading individual key-value pairs).

FDB_STREAMING_MODE_MEDIUM

Data is returned in batches between _SMALL and _LARGE.

FDB_STREAMING_MODE_LARGE

Data is returned in batches large enough to be, in a high-concurrency environment, nearly as efficient as possible. If the caller does not need the entire range, some disk and network bandwidth may be wasted. The batch size may be still be too small to allow a single client to get high throughput from the database.

FDB_STREAMING_MODE_SERIAL

Data is returned in batches large enough that an individual client can get reasonable read bandwidth from the database. If the caller does not need the entire range, considerable disk and network bandwidth may be wasted.

FDB_STREAMING_MODE_WANT_ALL

The caller intends to consume the entire range and would like it all transferred as early as possible.

FDB_STREAMING_MODE_EXACT

The caller has passed a specific row limit and wants that many rows delivered in a single batch.

enum struct streaming_mode_t : int {
 iterator	= FDB_STREAMING_MODE_ITERATOR,
 small		= FDB_STREAMING_MODE_SMALL,
 medium		= FDB_STREAMING_MODE_MEDIUM,
 large		= FDB_STREAMING_MODE_LARGE,
 serial		= FDB_STREAMING_MODE_SERIAL,
 all		= FDB_STREAMING_MODE_WANT_ALL,
3F exact		= FDB_STREAMING_MODE_EXACT
};
