Choosing the next storage reads

Several requests cover overlapping parts of one object, and some requested bytes are already cached. We need to read each uncached byte once while limiting how much data we read per batch. Datum merges the overlaps, splits requests around cached data, and shortens the last read when necessary.

// Plan storage reads around cached data, with a limit on bytes read in one batch.
#include <datum/interval/metric.h>

#include <algorithm>
#include <array>
#include <cstdint>
#include <iostream>

namespace datum = ceph::salad::datum;
namespace iv = datum::interval;

int main()
{
    constexpr std::uint64_t MiB = 1024 * 1024;
    const std::array request_ranges {
        iv::bounds({0, 16 * MiB}),
        iv::bounds({8 * MiB, 16 * MiB}),
        iv::bounds({40 * MiB, 16 * MiB})
    };
    const std::array cache_ranges {
        iv::bounds({4 * MiB, 8 * MiB}),
        iv::bounds({20 * MiB, 4 * MiB}),
        iv::bounds({44 * MiB, 8 * MiB})
    };

    const auto requested = iv::compile_intervals(request_ranges);
    const auto cached = iv::compile_intervals(cache_ranges);
    const auto missing = iv::compile_intervals(iv::difference(requested, cached));
    const auto batch = iv::take(missing, 14 * MiB, iv::bytes);

    std::ranges::for_each(batch, [](const auto& part) {
        std::cout << '[' << part.lower().key() / MiB << ", "
                  << part.upper().key() / MiB << ") MiB\n";
    });
}

About the interactive example

The browser displays results generated by the C++23 Datum core for all 12,675 control settings. It replays these results rather than compiling C++ in the browser. The downloadable program computes the selection directly. The scenario models the cache-hit and cache-miss planning problem found in Ceph's write-log cache, with an added limit on data read per batch.
